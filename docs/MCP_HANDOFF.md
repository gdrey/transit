# Transit GTFS MCP handoff

Use this document to continue development or operate the Transit GTFS Workbench from a compatible chat application. It records the agreed behavior, the examples used to define it, and the implementation at the time of this handoff. The examples specify expected decisions. A fresh assessment against the imported feed is required to report whether an actual change is reflected.

## Goal and architecture

An operator can ask questions of a static GTFS feed, enter feed edits or bring in service alerts, check what the feed already reflects, run the remaining changes, and review and download the exact resulting ZIP. The workflow must work across agencies and model providers.

- **GTFS engine.** Owns feed import, exact ID and service-date resolution, checks, planning, writing, and verification. Keep the same operations available to the web app and MCP, independent of any language model. The [GTFS Schedule reference](https://gtfs.org/documentation/schedule/reference/) defines the field meanings and relationships.
- **Language interpretation.** The model converts text into bounded, structured proposals. Supply relevant feed data and use actual route, stop, platform, and trip records to resolve natural-language references. Validate the proposal before planning or writing. Use deterministic rules for clear cases, such as selecting all standard bus routes. A model answer alone is insufficient evidence of schedule coverage or a successful edit.
- **MCP.** Exposes the GTFS operations to a compatible chat host. Connect a running client to the server to use the tools. Point an LLM at this document and repository to give it the project context. Keep schemas and workbench rules provider-neutral so a host can supply its own model.
- **Web app.** Gives operators a direct workflow and a visual audit of what changed. The local workbench can accept an OpenAI-compatible model connection for the session. The hosted app is designed for server-provided AI with a cap, and currently supports deterministic operations with included AI unavailable.

## Run the workflow

1. **Import GTFS.** Choose an agency preset, enter a public HTTPS URL, or upload a ZIP. Presets populate endpoints without fetching feeds before the operator starts an import. Store the original ZIP and its SHA-256. Show agency, feed date range, and time zone. Schedule questions are about the loaded feed and its service dates.
2. **Inspect the original.** Filter by route, service date, and direction. Use one Marey chart with time on the horizontal axis and ordered stops on the vertical axis. Show consecutive pattern ranges on that same axis with collapse and expand controls. Selecting a trip reveals its ID and stop times. Show a light black-and-white map with station names where shapes are available.
3. **Enter requests and import notices.** Keep manual feed edits and service changes separate. Preserve source text, URL or feed provenance, retrieval time, structured active periods and source entity ID. Assign independent, human-readable workbench IDs such as `Change ID 1` and an edit ID for each manual request. Treat IDs as references to a specific intake record. Use source identity and revision information to track updates. Support pasted text, alert webpages when fetchable, GTFS-Realtime and source adapters. The [MTA Mercury decoder](../prototype/realtime_alerts.py) reads extended subway alert Protobuf data. [Public agency presets](../prototype/builtin-agency-presets.json) include MTA subway, Broward, SEPTA bus, and MBTA. Route and mode coverage can differ between a preset's schedule and alert sources. A blocked webpage should surface a source error and allow pasted text or another endpoint.
4. **Assess reflection against the imported original.** Give every alert and feed edit one result with concrete evidence. Imported, queued, and assessed are distinct states. Make assessment triggerable, run it automatically for supported imports when possible, persist the results, and show failures and remaining work. Small batches, such as 10 or 20 for a review exercise, help with triage. Recheck known requests when a new feed is imported and attach results to its hash so an older assessment cannot be mistaken for current evidence. Where necessary, provide a text clarification on the individual item and recheck with it.
5. **Review plans before writing.** Use compact collapsible rows with ID, source text, retrieved-on date, assessment, and plan. For a feed edit, show its type, exact route scope, proposed field, and before and after values so the operator can check the parse. For an alert, name the exact files, trip occurrences, stops, dates, and operations the writer will change. Keep verification and export in their later sections. Stage supported changes that are confirmed missing by default. Let the operator remove an item from the run and remove feed edits from the active list. Routine review does not require a yes or no decision for every item.
6. **Run the pipeline.** Start from the original feed and apply the staged tasks together. Show current item and total, the file or operation in progress, what completed, and what was excluded or remains blocked. Report completion only when all intended eligible changes are accounted for. If the draft is partial, name the omitted IDs and reasons. Rebuild from the original to reverse a selected edit.
7. **Inspect the updated schedule, compare, then export.** Keep these steps in sequence. Select a change ID to see a compact summary of route, date, direction, affected trips, and the original and draft schedules side by side on matched axes. Highlight additions, skipped service, and platform or time changes. Show a circle for a served stop and an X for a scheduled pass-through with no boarding or alighting. A removed stop should be identifiable from its baseline position and the comparison details. Resolve the draft against the actual output ZIP and verify the ZIP hash at download. Show built-in checks and any independent validation separately. Independent MobilityData reports require an available validator and successful runs on the actual feeds.

The interface should read like a compact notebook from import to output. Keep the GTFS URL and upload in Admin, the visualizations in the scrollable flow, and the active section header sticky. Use the left navigation and consistent section colors for orientation. Use Times New Roman for headings and green Courier New for GTFS filenames, with feed values set in monospace. Show route short names in rounded badges with the route color and an icon based on `route_type`. Keep intake, assessment, plan, execution, and comparison easy to distinguish.

## Assessment and modeling rules

| Result | Evidence and action |
| --- | --- |
| ✓ Already reflected in GTFS | Show positive evidence from relevant service dates, trips or route records. Stage no edit. |
| ❗ Not reflected in GTFS | Show which expected changes are absent. Stage supported edits automatically and identify any writer gap. |
| ⚠️ Likely not reflected | Show evidence and the missing pieces. Clarify or verify before presenting the change as confirmed. |
| ✕ No schedule change / Not recommended for base schedule | Facility closures and short-lived operational delays typically belong here. Report the reason and skip static editing. |
| Not checked, needs clarification, or inconclusive | Keep queue status and uncertainty visible. Report missing feed coverage, incomplete job state, ambiguous IDs, or insufficient evidence. |

### Decide what service the notice describes

- Identify planned schedule changes and separate them from current disruptions. A planned platform move or planned added stop can affect the schedule. An elevator closure, entrance closure, or trains currently delayed generally does not. A single notice can contain several changes with different route, direction, station, and timing scopes. Check each operation and preserve the shared source ID.
- Check actual `trips.txt` and `stop_times.txt` records, weekly `calendar.txt` and exceptions in `calendar_dates.txt`. Resolve directions using trip patterns, stop order, and headsigns. Direction IDs `0` and `1` do not carry universal geographic meanings. A station may have multiple boarding stop IDs. Use `stops.txt` and parent-station relationships to map names and confirm platforms.
- Prefer the alert's structured active periods when natural-language timing is approximate or ambiguous. Retain both forms and record material assumptions. A notice at 9:30 and a structured period at 9:30:50 can describe the same change. Use agency-local time, service dates and GTFS times beyond `24:00` for overnight and weekend work. Use interval bounds consistently. For the structured skip check, start is inclusive and end is exclusive.
- Match the trip at the relevant point in the notice. For a station affected from 05:00 to 10:00, find trips passing that station in the window, even if they left the terminal earlier. Apply the resulting service variant to the whole trip. Apply frequency windows at the referenced terminal or point, depending on the alert. Show feed coverage gaps, and require positive evidence before calling a change already reflected.
- Resolve obvious wording or names from GTFS evidence, and state material assumptions. If plausible interpretations lead to different trips, dates, stops or platforms, ask a specific question. When the needed records exist in the feed, get trip-level evidence through the engine even if the interpretation prompt only received a compact context.

### Write a date-scoped, traceable change

| Change | Plan for relevant GTFS records |
| --- | --- |
| Route metadata | Update resolved `route_id` rows in `routes.txt`. Start with `route_color` and `route_short_name`, preserve other fields, and show each old and new value. For all standard buses, select `route_type=3`; trolleybus `11` is separate. Use a six-character RGB hex value without `#`. |
| Platform only | Resolve source and target boarding stop IDs using `stops.txt` and real trip records. Split service for affected occurrences, change `stop_times.txt` `stop_id`, and preserve timings where appropriate. Inspect shape and transfer dependencies before treating the edit as complete. |
| Stops skipped | For a train still passing on the same path, keep the timed record and set both `pickup_type` and `drop_off_type` to `1`. Removing a stop row may be appropriate when the actual trip pattern changes. Keep the chosen representation visible in the plan and chart. |
| Added stops and local running | Search for a representative trip of the same route and direction with the requested stops. Prefer complete compatible donor patterns, then compatible linked segments. Insert timed `stop_times.txt` rows in the correct order, retain reasonable anchor times, and mark estimated calls. Replace each affected occurrence once. |
| Reroute | Find the endpoints and the between-endpoint pattern on the named route or routes. Use compatible donor segments for path and stop order. Replace the affected part of `stop_times.txt`, reconcile running times with the unchanged ends, and assign the appropriate shape to the trip variant where geometry is available. |
| Full or partial suspension | Remove affected occurrences from scheduled service for a full suspension. For a partial suspension, create short-turn or split-trip variants for the operating segments; set terminal stops, headsigns, times, and platforms. Model other routes' compensating stops as their own operations. |
| Frequency | Check actual spacing at the relevant location and direction. For an “every N minutes” period, anchor to the alert window at that location and create departures at the stated interval through the period. Check the handoff from and to regular service to avoid overlapping departures or unintended service gaps. Choose the appropriate explicit trips or `frequencies.txt` encoding based on feed semantics. |
| Replacement bus | Draft separate static bus service with `route_type=3`, bus stops and date-scoped trips. Prefer agency-provided details. The reviewed fallback permits rail-based provisional times and straight-line geometry between confirmed or reviewed stops. Label those estimates, indicate the absence of realtime, and handle rail suspension separately. |

Split existing `service_id` and `trip_id` assignments by affected service dates and operation sets. Use `calendar_dates.txt` additions and removals and retain or adjust `calendar.txt` as needed. Preserve service on every unaffected day. Compose compatible changes on the same `(trip_id, service_date)` into a single variant and carry all contributing change IDs. Deduplicate equivalent operations. Use publication time to identify the likely intended revision when a source explicitly supersedes an older notice. When there is a real conflict, withhold the conflicting work and surface both IDs and the newer timestamp for review. The current writer raises a conflict and reports recency when known. Automatic precedence by latest timestamp alone is outside the agreed policy.

Where `shapes.txt` exists and an edit affects geometry, update the shape, `trips.txt` `shape_id`, and applicable `shape_dist_traveled` values and references. Follow real trip segments whenever defensible. Review dependent records such as transfers and frequency entries when their referenced trips or stops change. For missing geometry or timing, show a clearly marked draft estimate or ask for review. Straight-line bus sketches are approximate. A feed without shapes does not require adding them for routine platform or skip edits.

Keep an activity record keyed by change and output version. Capture source and retrieval time, evidence and assumptions, rule or operation used, affected files and before and after values, action and result, reasons for exclusions, original and output hashes, and validation status. Keep session credentials out of all logs and exported artifacts.

## Reviewed examples

Use these examples as regression cases for interpretation, trip resolution, and writing. Dates, windows and stop names below describe the exercise; resolve the exact feed values at runtime. Change numbers refer to the review batch in which they were discussed.

| Input or case | Expected behavior |
| --- | --- |
| Miami-Dade Route 150 on Sunday, and does it go to South Beach? | Resolve the route, pick an actual Sunday service date, check calendar exceptions and read the matching stop patterns. Answer with evidence from those trips and keep live service separate. |
| Financial District Metromover station closure from October 24, 2026; Brickell Loop still runs | Check service at the station while confirming loop trips remain. November 16 was the end date used for the exercise. For production use, record the explicit end or structured period; the “five weeks” wording alone yields a different end. Preserve the loop and apply the bypass only within scope. |
| Downtown `1` skips 125 St, 116 St–Columbia University, Cathedral Pkwy (110 St), and 103 St, weekends Nov 20–Dec 21, Fri 11:45 p.m. to Mon 5 a.m. | Expand applicable weekend active periods. Match downtown trips at the four physical stops and include after-midnight times on the proper service day. Check each named stop and show served versus skipped markers. |
| `Q` via `R` in both directions between Canal St and DeKalb Av, Nov 16–20, 11:30 p.m. to 5 a.m. | Interpret “Rin both directions” as “R in both directions” where the text and feed support it. Compare ordered segments in both directions. Plan replacement calls, compatible donor times and shape, and keep the existing trip ends. This requires a general reroute writer. |
| `C` via `F` and `D` between Jay St–MetroTech and 59 St–Columbus Circle | Look for the proposed routing on the `C`, then check compatible `F` and `D` segments in each direction. Match stop order, timing anchors and shape joins before building a variant. |
| Downtown `A` makes local stops at 50 St, 23 St, and Spring St | Check actual downtown `A` trips in the active windows. Prefer a compatible downtown `A` that makes all three stops. If none fits, assemble a representative pattern from verified segments, favoring the `A`, with a coherent shape and marked estimates where needed. |
| `J` express makes local stops in both directions at “Hugh Street,” Lorimer, and “Flushing Street” | Try the feed's Hewes St, Lorimer St and Flushing Av names and validate candidate matches against the `J` in both directions. Inspect trip-level stop times in each window. Stage supported missing calls; ask only about unresolved scope or stop identity. |
| Jamaica Center-bound trains board from the express track at Broadway Junction | Classify as a planned platform change. Match the affected route, headsign, station and direction, then prove the target express platform stop ID using schedule evidence. A platform estimate requires review. |
| Manhattan-bound `B` adds Neck Rd and Avenue U, versus uptown `4` running with delays | Check the planned `B` trips for both calls and plan missing ones. Keep ordinary `4` delays out of the base schedule. Elevator and entrance closures likewise require no schedule change. |
| `5` runs every 20 minutes | Start from each relevant active period, use its opening time as the anchor at the contextual location in each direction, and check cadence and handoffs to ordinary service. |
| Manhattan-bound `7` skips four stops, boards at Junction Blvd from the Flushing-bound platform, and runs every eight minutes during days and evenings | Assess the stop skips, platform move and frequency separately. Compose compatible changes on the same occurrence, preserving their own windows. Report any unwritten component in the run result. |
| Weekend `C` ends at 145 St on the lower-level `D` platform, with no `C` to 168 St and additional `A` stops | Model `C` short turns, platform and dated route segment, and assess compensating `A` stops separately. Use existing turnback patterns and times where possible. |
| Rockaway Park Shuttle suspension with buses between Beach 67 St and Rockaway Park–Beach 116 St | Separate the dated rail suspension and replacement bus. Approved for a clearly labeled estimated static draft if agency times or geometry are unavailable, using reviewed bus stops, rail-based times, and approximate straight-line shapes. |
| Changes 6 and 7 affect the same trip | One resulting trip variant can include both added and skipped stops. Show each change ID's evidence and the original and modified charts. A skip and an add for the same stop on the same occurrence can constitute a conflict. IDs alone do not identify the alerts in other imports. |
| Change 15 says weekend “all day” while structured periods describe day and evening; Change 19 has Friday-night ambiguity | Use structured active periods when in doubt and avoid treating small wording differences as blockers. For Change 19 the final instruction superseded the earlier Friday-night suggestion: use the alert's actual periods. |
| “Change all buses to orange,” “change route 1 to bright teal,” or “change this route short name” | Use `routes.txt`, resolve the requested scope to exact IDs, and show type, edit ID, old and new values. The standard all-bus shortcut sets `route_color=FFA500` and preserves other modes. Resolve or clarify the RGB for subjective colors and route names with multiple matches. |

## Interfaces and current implementation

**Hosted.** Open the [Transit Workbench](https://transit-workbench.vercel.app/), import a feed, and use **Connect an MCP client** to get a private session credential. Configure `https://transit-workbench.vercel.app/mcp` for Streamable HTTP with `Authorization: Bearer <session-token>` in a compatible host. `open_workbench` can show a compact MCP Apps schedule and review panel, with a browser link for the full workflow. Some clients require OAuth. The temporary pairing flow for those clients is still open. The app itself supplies the session token; model provider keys have a separate purpose. [Hosted setup and client configuration](../hosted/README.md).

| Task | Hosted MCP tools in [app.py](../app.py) |
| --- | --- |
| Bring in an agency | `list_agencies`, `import_agency(agency_id)`, `import_agency_alerts(agency_id)` |
| Inspect the schedule | `feed_summary`, `list_routes(query)`, `scheduled_trips(route_id, service_date, limit)` |
| Read or check alerts | `review_alerts(limit)` reads saved assessments; `check_skipped_stops(route_id, direction_id, stop_ids, timezone, windows)` checks an already resolved skip proposal |
| Stage and review a draft | `stage_route_edit(route_id, field, value)` stages a single exact-ID color or short-name edit; `review_pipeline`, `run_pipeline`, `review_output` |
| Open the visual | `open_workbench` |

The hosted tools use the same session and processing engine as the browser. Browser intake and worker assessment cover more flows than the published MCP tool surface. In particular, the MCP does not yet expose a general way for a chat model to submit arbitrary alert text, supply a full interpreted multi-operation plan, provide clarifications, and run bulk assessment using its own model. `review_alerts` should be treated as a saved-result reader. The [local stdio server](../prototype/mcp_server.py) is read-only and exposes `feed_summary`, `search_routes`, `scheduled_trips`, and `check_skipped_stops` against the locally loaded feed. Local launch and client setup are in the [repository README](../README.md).

For a schedule question such as “Is the G running on this day?”, call `feed_summary`, resolve the short name with `list_routes(query="G")`, then use the returned `route_id` and an explicit `YYYY-MM-DD` service date in `scheduled_trips`. A trip list can establish scheduled departures. Answering which stops are served requires stop-level evidence, available in the browser explorer or engine. For a supported write, inspect `review_pipeline` before `run_pipeline`, then use `review_output` to report the exact archive, verification and exclusions.

| Area | Implementation and remaining gap |
| --- | --- |
| Interpretation and checks | See [interpretation schema](../prototype/assistant-interpretation.schema.json), [resolved skip contract](../prototype/alert-contract.schema.json), [manual edit contract](../prototype/manual-edit.schema.json), [assistant bridge](../prototype/assistant_bridge.py), and [assessment queue](../prototype/assessment_queue.py). The engine can check or propose some changes that have no writer. Publish a typed proposal and evidence interface to give other chat models the same workflow. |
| Writing | [Route edits](../prototype/manual_edits.py) and the [service writer](../prototype/platform_edit.py) cover route color and short name, selected platform changes, skip-by-no-boarding, and donor-based added stops. Compatible operations can share a variant. General reroutes, full and partial suspensions, frequency edits, replacement buses, and general shape reconstruction still need full pipeline writers. Existing shapes can be preserved without validating the route geometry. |
| Verification | [Output manifest](../prototype/pipeline_output.py), [checks](../prototype/feed_validation.py), and [comparison data](../prototype/comparison_data.py) are the entry points. The archive and report are hashed and the implemented checks inspect archive contents. Independent MobilityData validation is optional locally and requires separate deployment to produce hosted reports. Treat any missing report as unavailable. |
| Temporary storage | Vercel serves FastAPI. [Neon stores compressed session files](../backend/hosted_runtime.py) and the existing SQLite engine runs in isolated scratch space. A browser import starts a private session and access expires after two hours. **End session** removes active data and revokes access. Expired records are purged separately from provider backup retention. A normalized Postgres schedule importer exists as an experiment. The live workflow uses the temporary snapshot store. |
| Model access | The [included AI pilot](../hosted/README.md#included-ai-pilot) uses a server provider with caps of ten calls per session and fifty total, and up to five model calls per alert batch. Hosted included AI was unavailable at handoff. Hosted visitors have no key field. The local optional connection holds a user-supplied credential transiently. Send only relevant alert or edit text and GTFS context to the model and keep all credentials server-side or session-only as applicable. |

## Where to pick up

1. Reproduce a read-only schedule check, a supported compound trip edit, and the archive review using one public feed. Verify the selected source hash, date-specific records and exact output hash. Use `tools/list` on the live server before relying on any tool described here.
2. Add provider-neutral MCP calls to stage a bounded interpreted request, look up relevant route, station, platform and trip evidence, run deterministic assessment, accept clarifications, and return a specific plan. The chat host can then supply natural-language interpretation even when hosted included AI is unavailable.
3. Use the reviewed examples to extend assessment and writers together. Prioritize donor segment and shape handling for reroutes and short turns, then frequency and provisional replacement bus service. Cover date rollover, existing reflected changes, conflicting and compatible changes, and correct untouched service outside the window.
4. Keep a per-feed record of proposals, evidence, and versions within the temporary session. Check original-versus-output records and chart alignment before promising an export. Add canonical validation and retryable jobs as deployment support permits.

For product scope see the [PRD](PRD.md) and the shorter [modeling policy](MODELING_POLICY.md). For the current deployment use the [hosted README](../hosted/README.md). The earlier [hosting proposal](HOSTING.md) describes an exploratory architecture.
